diagrams/DK2-01-pipeline.tldr

"A common mistake: thinking Docker is one thing you 'run'. It's a pipeline with three layers."

  • Dockerfile = the recipe. Plain text: what to start from, what files to include, what command to run.
  • Image = the result of building the recipe. A blueprint. Inert: it does nothing until you run it.
  • Container = a running instance. The building you can walk into.

"Define once (Dockerfile), build once (image), run as many identical copies as you need (containers)."

YOUR EDITOR · Lab step 1

Your first Dockerfile

docker-lecture/Dockerfile (no extension)

FROM alpine:latest
CMD ["echo", "hello world!"]

FROM

Start from an image already published on Docker Hub. Docker pulls it, then runs the rest of the file.

CMD

The command that runs when the container starts. A list of strings. Only one per Dockerfile.

A Dockerfile is not magic: every line is an instruction you can read.

** HANDS-ON, about 2 minutes. ** Create the file in the editor, named exactly Dockerfile: capital D, no .txt.

  • alpine = a very small Linux, about 8 MB. We opened a shell in it in Lecture 1.
  • CMD: print "hello world!", then the container exits.
  • Remember Lecture 1: latest isn't "stable". The curriculum uses it here for simplicity; the homework is a good place to pin alpine:3.20.

Windows Notepad may save Dockerfile.txt: check with ls (or dir).

YOUR TERMINAL · Lab step 2

Build it, find it, run it

$ docker build -t hello-docker .
#4 [1/1] FROM docker.io/library/alpine:latest
#5 naming to docker.io/library/hello-docker done

$ docker images
IMAGE                 ID             DISK USAGE
hello-docker:latest   2a10af81544d       8.42MB

$ docker run hello-docker
hello world!

The two flags

-t hello-docker = tag: a readable name for the image

. = "use the Dockerfile in this folder". Don't forget the dot!

You just did all three

Dockerfile → build → image → run → container

** HANDS-ON, about 3 minutes. ** Thumbs up in chat on "hello world!".

  • Build output: lines starting #1 #2… are steps. Find FROM and naming to … hello-docker. (Shortened on the slide.)
  • "Where is the image stored?" Inside Docker. docker images lists them. Older Docker shows REPOSITORY TAG IMAGE ID CREATED SIZE: same info.
  • docker run created a container, which ran echo, then exited.

"'docker buildx build' requires 1 argument" → the dot is missing. "failed to read dockerfile" → wrong folder or file named Dockerfile.txt.

YOUR EDITOR + TERMINAL · Lab step 3

Put a file inside the image

message.txt

Hello from inside the container.

Dockerfile (replace it)

FROM alpine:latest
WORKDIR /app
COPY message.txt /app/message.txt
CMD ["cat", "/app/message.txt"]
$ docker build -t file-demo .
#6 [2/3] WORKDIR /app
#7 [3/3] COPY message.txt /app/message.txt

$ docker run file-demo
Hello from inside the container.

WORKDIR /app = make and go into /app inside the image

COPY a b = from your folder → into the image (COPY . /app/ = everything)

** HANDS-ON, about 4 minutes. **

  • New tag file-demo, "so we don't overwrite the previous image".
  • Point at the build steps: [2/3] WORKDIR, [3/3] COPY. Each Dockerfile line is a step.
  • cat instead of echo: print the file we copied in.
  • "Key Docker moment: your file is now part of the image. Anyone who builds this Dockerfile gets the same file, in the same place, every time."

"message.txt: not found" during build → the file isn't next to the Dockerfile, or is named message.txt.txt.

YOUR TERMINAL · Lab step 4

Look inside your own image

$ docker run -it --rm file-demo sh
/app # pwd
/app                  ← WORKDIR
/app # ls
message.txt           ← COPY
/app # cat message.txt
Hello from inside the container.
/app # exit

What happened?

Adding sh at the end replaces the CMD for this one run

You start in /app because of WORKDIR

This is how you debug: "is my file really in there?"

If you can't see it, open a shell and look.

diagrams/DK2-03-cleanup.tldr

"Docker does not clean up after you. Every build and every run leaves something behind."

  • Containers depend on images. So: containers first, then the image.
  • Stopped containers still exist, and docker ps hides them. That's the homework question "Why don't stopped containers appear with docker ps?"

"Let's find our mess."

YOUR TERMINAL · Lab step 5

Where did my containers go?

$ docker ps
CONTAINER ID   IMAGE   …   STATUS   NAMES    ← empty?!

$ docker ps -a
CONTAINER ID   IMAGE          …  STATUS       NAMES
2c35db8c8953   file-demo      …  Exited (0)   affectionate_shaw
a239a14bf944   hello-docker   …  Exited (0)   stupefied_blackburn

$ docker rm stupefied_blackburn        # use YOUR name
stupefied_blackburn

$ docker run -d --name sleeper alpine sleep 300
$ docker rm sleeper
Error response from daemon: cannot remove container "sleeper":
container is running: stop the container before removing
or force remove
$ docker rm -f sleeper
sleeper

Three ways

docker rm name
stopped container

docker rm -f name
running: stop + remove. Use on purpose!

docker run --rm image
removed as soon as it exits: no mess

** HANDS-ON, about 4 minutes. **

  • docker ps = running only. Ours ran for a split second, so: empty. "Beginners think they're gone. They're not."
  • docker ps -a = all. Names are random (Docker picks adjective_scientist). Everyone's names are different: use yours. Tab completes them.
  • sleeper: -d runs it in the background, sleep 300 keeps it alive 5 minutes. Now docker ps shows it as Up.
  • The red error is real (dry run, Docker 29). Then -f.
  • Last: --rm. "For one-off containers, this is the best practice."

Columns trimmed on the slide; theirs also show CREATED and PORTS.

YOUR TERMINAL · Lab step 6

Why won't my image delete?

$ docker rmi file-demo
Error response from daemon: conflict: unable to remove
repository reference "file-demo" (must force) - container
2c35db8c8953 is using its referenced image b350f29a4f26

$ docker rm affectionate_shaw          # 1 · the container
$ docker rmi file-demo                 # 2 · then the image
Untagged: file-demo:latest
Deleted: sha256:b350f29a4f26…

$ docker images                        # gone

The rule

Images can't be removed while a container depends on them

Order: stop → remove the container → remove the image

Same tag again?

docker build -t file-demo . twice moves the name to the new image. The old one stays (untagged) until nothing uses it.

** HANDS-ON, about 3 minutes. ** The IDs and names on their screens differ: read theirs.

  • Read the error slowly: "container 2c35… is using its referenced image". Docker is protecting you.
  • Then the curriculum's order: docker rm -f container_name, docker rmi image_name.
  • We'll rebuild file-demo in 7 minutes, so deleting it is fine.

Untagged images: Docker 29 hides them from docker images (older versions show <none>). docker image prune removes them. Mention only if asked.

diagrams/DK2-04-copy-vs-mount.tldr

Curriculum objective: "connect your local machine's files to a running container to support real development workflows". The run.sh in a few minutes also mentions a bind mount.

  • COPY = a photocopy at build time. Edit the original: the photocopy doesn't change.
  • Bind mount (-v) = a window into your folder. The container sees your files live.
YOUR TERMINAL · Lab step 7

Edit on your laptop, no rebuild

$ docker build -t file-demo .
# edit message.txt in your editor, save:
#   Edited on my laptop.

$ docker run --rm file-demo
Hello from inside the container.   ← old (COPY)

$ docker run --rm -v "$PWD":/app file-demo
Edited on my laptop.              ← live!

Read the flag

-v "$PWD":/app
my current folder → /app in the container

PowerShell:
-v "${PWD}:/app"

Git Bash: put MSYS_NO_PATHCONV=1 before docker

** HANDS-ON, about 2 minutes. ** (Rebuild first: we deleted file-demo on slide 11.)

  • Without -v: the old text. COPY froze it at build time.
  • With -v: the new text. Nothing rebuilt.
  • "This is how you'll develop with Docker later: code on your laptop, run it in the container."

Git Bash rewrites /app into a Windows path; MSYS_NO_PATHCONV=1 stops that.

YOUR EDITOR + TERMINAL · Lab step 8

Stop retyping: run.sh

#!/usr/bin/env bash
set -e
# variables you may update to target the correct file
IMAGE_NAME="lecture2-demo"
CONTAINER_NAME="lecture2-container"
# this will rebuild the image within the docker engine
echo "Building image: $IMAGE_NAME"
docker build -t "$IMAGE_NAME" .
# this will run the container and automatically remove it upon completion
echo "Running container with bind mount..."
docker run --rm --name "$CONTAINER_NAME" "$IMAGE_NAME"
$ ./run.sh
bash: ./run.sh: Permission denied
$ chmod +x run.sh
$ ./run.sh
Building image: lecture2-demo
…
Running container with bind mount...
Edited on my laptop.

Windows: run it in Git Bash or WSL, not PowerShell or Command Prompt

** HANDS-ON, about 3 minutes. ** Copy run.sh from the lab page (word for word from the curriculum).

  • Run it before chmod on purpose: "Permission denied" (seen in the dry run, in bash; zsh on a Mac words it a little differently, same meaning). A new file isn't allowed to run as a program. chmod +x = make it executable.
  • set -e = stop at the first error.
  • Every ./run.sh = build + run + clean up. --rm means no pile-up: check docker ps -a.
  • The output is whatever is in their message.txt (they edited it on slide 14).
  • Stretch for fast students: add -v "$PWD":/app to the docker run line, so edits show without a rebuild.

"Teams codify repeated steps into scripts, Makefiles or Compose files. Same mindset: fewer human errors."

Two tools you'll need for the homework

Task 3 · environment variables

ENV NAME="value" in a Dockerfile sets one

docker run --rm -e NAME="other" image overrides it (the stretch)

Watch out: CMD ["echo", "$NAME"] prints $NAME literally. The list form doesn't run a shell, so nothing swaps the variable in. sh -c "…" does.

Task 4 · a script

COPY the script in, then run it with its interpreter: sh or python

Watch out: CMD ["./hello.sh"] on a file without execute permission:

exec: "./hello.sh": permission denied

Same lesson as run.sh.
